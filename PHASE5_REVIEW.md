# Phase 5 review — component and request-flow tracing

Validated on 2026-10-30 against a read-only HBEC workspace and the local test harness. `npm run lint`, `npm test` (25 tests, including 6 new pure-parser tests and a new Flows-view webview test), and `ARCHI_TEST_WORKSPACE=/home/shadowe/Projects/HBEC npm run test:extension` all pass. The extension-host run exercises the new extractors directly against HBEC's real source (not fixtures) and asserts on two concrete, previously audited examples: the student-login HTTP route and the password-reset-email Celery task.

## What was built

- **Django route resolution** (`src/pythonRoutes.ts`, pure parser; `src/componentWorkspace.ts`, workspace orchestration). A service's root `config/urls.py` (falling back to a top-level `urls.py`) is parsed for its `urlpatterns` list; each `path()`/`re_path()` entry is either a leaf (resolves to a view) or an `include()` (resolves to a dotted module path like `apps.accounts.urls`, which is mapped to `apps/accounts/urls.py` and recursively parsed, prefix-composed, up to a depth of 4). Raw-string patterns (`r"^detail/..."`) are handled; dynamic prefixes (a variable instead of a string literal) are reported as diagnostics rather than fabricated. HBEC's real layout — central router + per-app `urls.py`, with some apps (`accounts`) split across several included modules (`urls.py`, `parent_urls.py`, `subscription_urls.py`, `payment_urls.py`) at different prefixes — was the concrete shape this was built against, confirmed by a dedicated research pass before writing any parser code.
- **Celery task/trigger tracing** (`src/pythonTasks.ts`). `@shared_task`/`@app.task`-decorated functions are found (including the explicit `name="..."` kwarg form used in `apps/ai_gateway/tasks.py`); `.delay()`/`.apply_async()` call sites are found by their object symbol across a service's `tasks.py`/`views.py` files and matched to a task definition by symbol name. A task node's evidence array holds both its definition line and every matched trigger-site line, so "where is this task called from" is answered without inventing a synthetic caller node — a graph-shape choice made to keep every evidence-bearing node real.
- **Flows view** (`media/main.js`, `media/style.css`): a third view mode alongside System and Data, scoped by owning service, showing route and task nodes with distinct styling, `serves` edges from the service to its routes, and the existing Explore/Open-in-system-map/Back cross-navigation generalized to all three modes (not just System↔Data).
- Shared Python-AST helper functions (`slice`, `children`, `callName`, `literal`, `firstArgument`, `keyword`, `findCalls`, `appFromPath`, `lineOf`) were exported from `pythonModels.ts` rather than duplicated, since both new parsers needed the same `@lezer/python`-tree primitives already built and tested in Phase 3.

## HBEC validation

The extension-host test asserts, against HBEC's actual `student-backend` source (not a fixture): `config/urls.py`'s `path("api/auth/", include("apps.accounts.urls", ...))` composes with `apps/accounts/urls.py`'s `path("login/", StudentLoginView.as_view(), ...)` into a route node labeled `/api/auth/login/` with `view: "StudentLoginView"`, a `serves` edge from the `student-backend` service node, and working source navigation. It also asserts that `apps/accounts/tasks.py`'s `send_password_reset_email_task` is found with at least two evidence entries (its `@shared_task` definition plus its `.delay()` call site in `apps/accounts/views.py`), both independently navigable.

Running the full extractor across all six HBEC Django services (`student-backend`, `admin-backend`, `harness`, `notifications`, `payments`, schools) produced **423 component nodes and 363 edges from 3 diagnostics** — all three diagnostics are honest, expected gaps, not bugs:
- `apps/sbp/urls.py:13`: `path('', include(router.urls))` — a DRF router's dynamically generated URL list, which is a variable, not a string literal, so it is correctly left unresolved rather than guessed.
- Two services' root `urls.py` include `django_prometheus.urls`, a third-party package outside the workspace — the same category of honest gap as Phase 3's `django.contrib.auth.models.User` references.

## Scope decisions

- **No JS/TS client-call extraction.** Resolving a React/Vite `fetch`/`axios` call to a specific backend route (e.g. `STUDENT/Frontend/src/features/auth/services/authService.ts`'s call to `/auth/login/`) was investigated and found real and traceable, but doing it properly — matching the project's "prefer AST/parser... to broad regex" rule — would mean adding a JS/TS parser dependency (e.g. `@lezer/javascript`) and a second extractor family, which is a larger addition than this phase's time budget supports well. It is deferred rather than attempted with regex. This phase's exit gate ("at least two HBEC paths... one HTTP, one event or queue path... with source links and honest gaps") is still met: the already-existing Compose-level service-to-service HTTP edges (Phase 2, e.g. `admin-backend` → `student-backend` via `STUDENT_SERVICE_URL`) combined with the new per-service route list let a user follow an HTTP path from one service, across the Compose layer, into the specific endpoint and view that serves it — without needing the frontend hop resolved to satisfy "component-level work must outperform simply opening Context Graph," since Context Graph has no Django-URL-composition or Celery-task-linking awareness at all.
- **No full call graph.** Per the plan's explicit instruction ("focused route and event views, not a full-workspace call graph"), the Flows view is scoped to one service at a time, mirroring the Data view's owner-scoping pattern rather than introducing a new interaction model.
- **Graceful degradation preserved.** `componentWorkspace.ts` never throws on a missing root `urls.py`, an unresolved `include()` target, or a malformed task file — each produces a diagnostic and the rest of the graph (system map, data map, and other services' flows) stays usable, consistent with the plan's "keep the system and data maps usable when one language extractor fails or is unavailable."

## Visual testing and a scoping fix found by it

Since this environment cannot drive a real VS Code desktop GUI (see the MVP-gate note in `IMPLEMENTATION_PLAN.md`), the webview was visually validated a different way: a standalone HTML harness (outside the repo, in a scratch directory) loads the unmodified `media/main.js`/`media/style.css` with a VS Code Dark+ variable approximation, is fed the *real* HBEC-extracted graphs (via the same pure `analyzeCompose`/`analyzePythonModels`/`parseUrlModule`/`parseCeleryFile` functions the extension itself calls, just driven with `fs` instead of `vscode.workspace.fs`), and is screenshotted headlessly with `google-chrome --headless=new`, including scripted interaction scenarios (click a group, switch view mode, select an owner/app, click a node) before each screenshot.

This caught a real design-conformance gap: `student-backend` alone declares 129 routes. The Flows view had no per-app scoping (unlike the Data view, which already scopes by app), so selecting a service rendered all 129+ route/task nodes as one flat alphabetically-sorted grid with a "serves" edge from an off-screen service node to each one — exactly the "not focused" anti-pattern Phase 5's own text says to avoid ("build focused route and event views, not a full-workspace call graph"). Fixed by extending the existing app-select control (already built for the Data view) to the Flows view: `componentWorkspace.ts`'s task nodes now carry an `app` field (derived the same way model nodes already do, via `appFromPath`), `main.js`'s `populateApps()` now sources apps from whichever graph is active, and the Flows view's `project()` filters by the selected app. While investigating the resulting screenshot, also found that drawing a "serves" edge from the owning service to every one of its routes added visual noise without information (the owner is already shown in the toolbar), so the Flows view now renders only route/task nodes, no service hub node — an edge-count-to-information-ratio observation that wouldn't have surfaced without actually looking at the rendered output. A regression test (`test/webview.test.cjs`) now exercises two apps on one service and asserts the app filter actually narrows the rendered set.

## Bug found and fixed during this work

`joinRoutePath` originally stripped the trailing slash from a composed route (`api/auth/` + `login/` → `api/auth/login`), which would have misrepresented every Django route Archi extracts, since Django/DRF routing is slash-sensitive and HBEC's endpoints are all trailing-slash. Caught by the HBEC integration assertion expecting the real route `/api/auth/login/` and failing against the stripped-slash output; fixed by preserving a trailing slash when the last composed segment had one, with a regression test (`joinRoutePath('api/auth/', 'login/')` must equal `'api/auth/login/'`, while `joinRoutePath('api/auth/', 'login')` without a trailing slash must not gain one).

An extension icon was also added this session (`media/icons/icon.png`/`.svg`, three connected nodes on a dark rounded-square background, matching the webview's own blue/green/orange accent palette), registered via `package.json`'s `icon` field, and confirmed legible at both 128px and 32px.
